# Global credentials file shared by all sessions — last-connector-wins cross-user overwrite

**ID:** vuln-0003
**Severity:** CRITICAL
**Found:** 2026-10-18 21:46:17 UTC
**Target:** http://host.docker.internal:8080
**Endpoint:** /api/connect.php
**CVSS:** 9.9
**Confidence:** Medium
**Fix Effort:** Medium

## Description

All connected sessions share one global credentials file, so each new Namecheap connection silently overwrites every other session's stored key and every connected session acts on whoever connected last.

## Evidence

Source excerpt from bootstrap.php:

```php
define('CRED_DIR', getenv('LANDING_CRED_DIR') ?: '/credentials');
define('CRED_FILE', CRED_DIR . '/namecheap.json');
```

connect.php on the authenticated transition:

```php
store_credentials([
    'username' => $username,
    'api_key' => $api_key,
    'client_ip' => $client_ip,
    'sandbox' => $sandbox,
]);
$_SESSION['nc_connected'] = true;
$_SESSION['nc_username'] = $username;
```

read_credentials() returns the shared file to any session passing require_namecheap_session(); no session keying exists anywhere in bootstrap.php. The pairable-session mechanism (client-chosen session IDs accepted) is dynamically confirmed in vuln-0002 against the live target.

## Impact

Any second connection silently replaces the first session's stored Namecheap key. The first session then reports the wrong account owner and proxies its domain/DNS calls through the second user's key, giving unauthorized access to another user's Namecheap account data while the first user's credentials are silently discarded.

## Counterevidence

Actively checked: (1) whether read_credentials() or require_namecheap_session() keys stored credentials to the session that created them — no session binding exists in bootstrap.php; (2) whether store_credentials() writes per-session paths — it writes one global path via tmp+rename; (3) whether domains.php/dns.php re-verify the caller owns the stored key — they only check the nc_connected flag; (4) whether disconnect.php scopes deletion to one session — it deletes the shared file for everyone. Residual limitation: the mock Namecheap endpoint is unreachable from the test container, so the A/B connect-success chain could not be replayed end-to-end.

## Confidence Rationale

The mechanism is statically conclusive from source (global single-file credential store read by every connected session), and the pairable-session mechanism (client-chosen session IDs accepted) is dynamically validated on the live target. The full A/B connect-success chain was not replayed because the mock Namecheap endpoint is unreachable from the test container.

## What Would Change This Severity

If the target were confirmed to be deployed strictly single-user (one landing session at a time), the cross-user impact would collapse to wrong-account attribution and this would drop to low.

## Technical Analysis

php/bootstrap.php defines CRED_FILE as a single global path (bootstrap.php:16-17). store_credentials() (bootstrap.php:52-64) wholesale-overwrites that one file via tmp+rename on every successful connect; read_credentials() (bootstrap.php:66-76) returns that same file to any session that passes require_namecheap_session(). php/connect.php:43-50 calls store_credentials() on the authenticated transition and sets $_SESSION['nc_connected']=true, but never keys the stored credentials to the session that created them. php/domains.php and php/dns.php call require_namecheap_session() and pass the shared credentials to nc_domains()/nc_dns_hosts(), so every connected session acts on whoever connected last. php/disconnect.php deletes the shared file for everyone. This pairs with the session-fixation finding (client-chosen session IDs are accepted), which lets an attacker replay a known cookie value and land on a connected session backed by the shared credentials.

## Proof of Concept

1. Session A connects with a first Namecheap key (the global creds file now holds A).
2. Session B connects with a second key — store_credentials() wholesale-overwrites the shared file with B.
3. Session A calls /api/status.php and /api/domains.php — A now reports B's username and proxies its calls through B's key.
4. This chain was not replayed end-to-end in this test environment because the mock Namecheap endpoint is unreachable from the test container; the mechanism is statically conclusive from source and the pairable-session mechanism it rides on is dynamically confirmed in vuln-0002.

```bash
# Session A connects
curl -s -c /tmp/a.jar -H 'Cookie: MULTIAI_LANDING=<random32hexA>' \
  http://host.docker.internal:8080/api/status.php
curl -s -X POST -b /tmp/a.jar -H 'X-Landing-CSRF: <csrfA>' \
  -d 'username=userA&api_key=aaaaaaaaaa&use_sandbox=1' \
  http://host.docker.internal:8080/api/connect.php

# Session B connects (overwrites the shared file)
curl -s -c /tmp/b.jar -H 'Cookie: MULTIAI_LANDING=<random32hexB>' \
  http://host.docker.internal:8080/api/status.php
curl -s -X POST -b /tmp/b.jar -H 'X-Landing-CSRF: <csrfB>' \
  -d 'username=userB&api_key=bbbbbbbb&use_sandbox=1' \
  http://host.docker.internal:8080/api/connect.php

# Session A now proxies B
curl -s -b /tmp/a.jar http://host.docker.internal:8080/api/status.php   # shows userB
curl -s -b /tmp/a.jar http://host.docker.internal:8080/api/domains.php  # served via B's key
```

## Remediation

Scope the credential store to the session that created it: derive the credentials path from the PHP session ID (for example CRED_DIR . '/' . hash('sha256', session_id()) . '.namecheap.json') in store_credentials(), read_credentials(), and delete_credentials(), and keep the existing lock-plus-atomic-rename write pattern. Alternatively, encrypt the stored credentials and bind the encryption key to the session so only the creating session can decrypt them; both approaches remove the last-connector-wins overwrite.

## Fix Verification

Security closure (reasoned, not executed): after the patch, read_credentials() resolves the per-session file sid(session_id()).namecheap.json under CRED_DIR, so session A's status/domains/dns calls resolve only A's own stored credential and can no longer resolve B's overwrite; wholesale overwrite of another session's credential file is eliminated by construction because every write is scoped to the writing session's SID. Bypass review: sibling call sites are store_credentials (scoped by the helper), read_credentials (scoped by the helper), and delete_credentials, which is updated in the same hunk to unlink only the calling session's file — the shared-file deletion path (one user's disconnect removing another user's stored key) is closed by the same scoping. Preserved behavior: a fresh session has no stored file, so require_namecheap_session() already fails closed with 401 "Stored connection is gone, connect again" before the change and after it, so the legitimate flow is unchanged. Repository checks: the proposed hunk compiles standalone — `php -l` clean in a /tmp sandbox build of the same lines (session_regenerate_id and per-session file resolution both valid PHP 8.4). Gap: no live A/B replay against the patched app because the mock Namecheap endpoint is unreachable from this test container.

## Assumptions

Assumes at least two separate browser sessions reach the app concurrently (in a single-user deployment the impact degrades to wrong-account attribution; in any multi-user or multi-tab usage it becomes cross-user credential misuse). Connect-success chain validated only statically — the mock Namecheap host is unreachable from the test container, so the A/B connect-success chain was not replayed end-to-end.
