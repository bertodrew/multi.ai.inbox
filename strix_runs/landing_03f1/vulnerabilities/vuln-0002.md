# Session fixation on Namecheap connect — client-chosen session ID accepted and never rotated on authenticated transition

**ID:** vuln-0002
**Severity:** CRITICAL
**Found:** 2026-10-18 21:45:53 UTC
**Target:** http://host.docker.internal:8080
**Endpoint:** /api/connect.php
**Method:** POST
**CVSS:** 9.6
**Confidence:** High
**Fix Effort:** Low

## Description

The landing app session uses PHP's default non-strict session mode and never rotates the session identifier when a Namecheap API key is connected, so an attacker can pre-set the session cookie to a known value and inherit the authenticated connection established on it.

## Evidence

Dynamic responses from the live target:

```http
GET /api/status.php HTTP/1.1
Cookie: MULTIAI_LANDING=9cdc672410784680891ec7a3d76d84d4

HTTP/1.1 200 OK
Set-Cookie: (none)

{"ok": true, "connected": false, "username": null, "sandbox": false, "csrf": "f0dc2a006b4f97bfc9cded8dc533d0b8", ...}
```

```http
POST /api/connect.php HTTP/1.1
Cookie: MULTIAI_LANDING=9cdc672410784680891ec7a3d76d84d4
X-Landing-CSRF: f0dc2a006b4f97bfc9cded8dc533d0b8
Content-Type: application/x-www-form-urlencoded

username=demo-user&api_key=0123456789abcdef&client_ip=1.2.3.4&use_sandbox=1

HTTP/1.1 401 Unauthorized
{"ok": false, "error": "API Key is invalid or API access has not been enabled"}
```

The 401 is the Namecheap API result, NOT the `403 {"ok": false, "error": "Invalid CSRF token, reload the page"}` response — the CSRF gate passed on the attacker-fixed session. The repository contains zero occurrences of `session_regenerate_id` or `session.use_strict_mode`.

## Impact

Any anonymous visitor can be locked into an attacker-known session ID. When the Namecheap connect flow completes on that session, the attacker replays the known cookie value and inherits the connected state, gaining full unauthorized access to the victim's Namecheap account data and domain/DNS configuration through the landing app's connected session.

## Counterevidence

Actively checked: (1) whether nginx or PHP config enforces session strict mode — no ini_set and no php.ini override in the repo, and the server accepted the chosen ID; (2) whether connect.php or bootstrap.php rotates the ID on the authenticated transition — zero occurrences repo-wide; (3) whether the cookie Secure flag limits fixation — HTTPS is optional in this deployment, the cookie Secure attribute depends on protocol detection and plain HTTP was used; (4) whether the CSRF token would block the replay — hash_equals against the same session's token, which the attacker fixed, so it does not. Residual limitation: the mock Namecheap endpoint is unreachable from the test container, so the connect-success replay of a mocked credential could not be driven end-to-end; every mechanical step before it was executed against the live target.

## Confidence Rationale

Dynamic PoC against the live target for every mechanical step: client-chosen session ID accepted (200, no reissued cookie), CSRF minted on it, and the CSRF gate passing on the fixed session (401 from the Namecheap call, not 403). The final connect-success replay was blocked because the mock Namecheap endpoint is unreachable from the test container; the PHP-side transition is fully traceable in source.

## What Would Change This Severity

If the target were confirmed to enforce session.use_strict_mode or to rotate the session ID on the authenticated transition, the fixation story would collapse and this would drop to informational.

## Technical Analysis

`php/bootstrap.php` calls `session_start()` with no `ini_set('session.use_strict_mode', '1')` hardening, so PHP adopts any client-presented session ID for `MULTIAI_LANDING` (verified dynamically: GET /api/status.php with a 32-hex tester-chosen cookie returned HTTP 200 with no Set-Cookie, and minted a CSRF token for that chosen session). `php/connect.php` sets `$_SESSION['nc_connected'] = true` and `$_SESSION['nc_username']` on that same session ID; no `session_regenerate_id()` occurs anywhere in the repository. Because the session ID is never regenerated on the authenticated transition, an attacker who fixates the cookie value obtains the connected session the victim establishes on it. The session cookie is HttpOnly and SameSite=Lax, which does not prevent an attacker from fixating the value on a plain-HTTP deployment.

## Proof of Concept

1. Pick a 32-hex session ID (the "fixed" value).
2. GET /api/status.php with only that fixed MULTIAI_LANDING cookie — confirm HTTP 200, no Set-Cookie reissue, and a CSRF token returned for the chosen session (proves session.use_strict_mode is off).
3. POST /api/connect.php with the same fixed cookie, the X-Landing-CSRF header set to that CSRF token, and valid-format credential fields — confirm the CSRF gate passes (the response is the Namecheap result, not "Invalid CSRF token").
4. In a real two-client scenario, the attacker would now replay the known cookie value and inherit the connected session created on it.

```bash
# (a) client-chosen session ID accepted by the server (use_strict_mode off)
curl -s -H 'Cookie: MULTIAI_LANDING=9cdc672410784680891ec7a3d76d84d4' \
  http://host.docker.internal:8080/api/status.php
# -> 200, Set-Cookie: None, body includes csrf for the attacker-chosen session

# (b) CSRF gate passes on the fixed session
curl -s -X POST \
  -H 'Cookie: MULTIAI_LANDING=9cdc672410784680891ec7a3d76d84d4' \
  -H 'X-Landing-CSRF: f0dc2a006b4f97bfc9cded8dc533d0b8' \
  -d 'username=demo-user&api_key=0123456789abcdef&client_ip=1.2.3.4&use_sandbox=1' \
  http://host.docker.internal:8080/api/connect.php
# -> 401 from the Namecheap API call, NOT 403 Invalid CSRF token
```

## Remediation

Set session.use_strict_mode=1 via ini_set before session_start in bootstrap.php so client-supplied session IDs are rejected, and call session_regenerate_id(true) on the nc_connected transition in php/connect.php (and equivalently on any other privilege change) so the anonymous pre-auth session ID is invalidated and a fresh server-issued ID is installed when a connection is established.

## Fix Verification

Applicability: fix_before hunks are verbatim copies of php/bootstrap.php lines 5-14 and php/connect.php lines 42-50 (read from the mounted checkout); the change adds one ini_set line before session_start and one session_regenerate_id(true) line before the nc_connected flags — nothing unrelated. Security closure (re-traced through the patched source; live replay blocked): after the patch, session.use_strict_mode=1 makes the runtime reject a client-chosen MULTIAI_LANDING ID (the accepted 32-hex value on GET /api/status.php with no Set-Cookie reissue is rejected instead of adopted), and session_regenerate_id(true) on the nc_connected transition destroys the pre-auth session ID the attacker fixed and installs a fresh server-issued one — the known-cookie replay that defines the fixation story now resolves to an unrelated empty session. Bypass review: sibling transition points are disconnect.php (privilege-losing, no rebind required) and dns.php/domains.php (read-only consumers of the already-authenticated state, no new principal installed), and equivalent malicious input classes were checked — a null byte, a 128-hex overlong ID, and an empty cookie value all fall under the same strict-mode rejection since PHP validates the ID format before opening the store. Preserved behavior: the anonymous session (cookie issuance, CSRF minting, status.php responses) is unchanged, and the connect flow's success path keeps its rate limiting, credential validation, and store_credentials() call; only the ID value changes. Repository checks: the extracted hunk compiles standalone — `php -l` clean on PHP 8.4.24, and the authenticated transition executed correctly in a /tmp sandbox build of the same lines. Gap: the mock Namecheap endpoint is unreachable from this test container, so the connect-success replay of a mocked credential against the patched app could not be driven end-to-end.

## Assumptions

Assumes an attacker can fix the landing cookie in a victim browser (HTTP deployment, HttpOnly cookie settable via crafted requests or a subdomain cookie-injection vector, no Secure flag requirement on plain HTTP) and that the victim completes the connect flow. Connect-success chain validated only partially — the mock Namecheap host is unreachable from the test container, so the connect-success step was not replayed end-to-end.
